M-02Estruturação de lógica (o módulo mais importante)

O objetivo aqui é reconstruir sua capacidade de ir de "eu sei o que quero" até código funcionando, sem IA.

O fluxo universal de qualquer automação

ENTRADA → VALIDAÇÃO → PROCESSAMENTO → TRANSFORMAÇÃO → SAÍDA

Praticamente todo script de automação/dados segue isso. Antes de escrever qualquer linha, responda:

  1. Entrada: de onde vêm os dados? (arquivo, API, banco, input do usuário)
  2. Validação: o que pode estar errado nos dados de entrada?
  3. Processamento: o que precisa ser calculado/filtrado/combinado?
  4. Transformação: em que formato final os dados devem estar?
  5. Saída: para onde vai o resultado? (arquivo, planilha, banco, e-mail)

Exemplo de decomposição real

Problema: "Preciso ler uma planilha de vendas, remover linhas inválidas, calcular o total por vendedor e salvar um resumo."

Como pensar (antes de codar):

ENTRADA:      arquivo Excel "vendas.xlsx"
VALIDAÇÃO:    linha sem valor numérico? vendedor vazio? valor negativo?
PROCESSAMENTO: agrupar por vendedor, somar valores
TRANSFORMAÇÃO: transformar em tabela vendedor -> total
SAÍDA:        salvar "resumo_vendas.xlsx"

Isso vira funções pequenas, cada uma com UMA responsabilidade:

def carregar_vendas(caminho):
    ...

def validar_linha(linha):
    ...

def calcular_total_por_vendedor(vendas):
    ...

def salvar_resumo(resumo, caminho_saida):
    ...

def main():
    vendas = carregar_vendas("vendas.xlsx")
    vendas_validas = [v for v in vendas if validar_linha(v)]
    resumo = calcular_total_por_vendedor(vendas_validas)
    salvar_resumo(resumo, "resumo_vendas.xlsx")

if __name__ == "__main__":
    main()

Note: main() só orquestra — ele não faz cálculo nenhum. Isso é separar lógica de negócio de entrada/saída, e é o que torna o código testável e fácil de debugar.

Quando criar uma função

Crie uma função quando: - você repetiria o mesmo bloco de código em outro lugar; - um trecho tem um nome óbvio ("validar linha", "calcular total") — se você consegue nomear, é sinal de que é uma unidade lógica; - você quer testar essa parte isoladamente; - a função main/o script está passando de ~20-30 linhas.

Sinal de função gigante demais: se você precisa rolar a tela para ler ela inteira, ou se o nome da função precisaria de "e" ("processar_e_validar_e_salvar") — quebre em partes.

Como decidir a estrutura de dados

Situação Estrutura
vários registros parecidos (linhas de planilha) list[dict]
associar uma chave a um valor único dict
preciso checar "já vi isso?" muitas vezes set
dado fixo que não muda (coordenada, RGB) tuple
preciso contar ocorrências dict ou collections.Counter
preciso agrupar por categoria dict de listas ({"categoria": [itens]})

Ruim (mistura tudo):

    with open("dados.csv") as f:

Melhor (lógica isolada, testável sem precisar de arquivo):

def calcular_total(valores: list[float]) -> float:
    return sum(valores)

def extrair_valores(linhas: list[str]) -> list[float]:
    return [float(linha.split(",")[2]) for linha in linhas]

def main():
    with open("dados.csv") as f:
        linhas = f.readlines()
    valores = extrair_valores(linhas)
    total = calcular_total(valores)
    print(f"Total: {total}")

Agora calcular_total([10, 20, 30]) pode ser testado sem nenhum arquivo.

Quando capturar, quando não capturar

Capture quando você sabe o que fazer com o erro (pular a linha, usar um valor default, tentar de novo).

Como pensar em Pandas (leia isto antes do resto)

A diferença entre código Pandas ruim e bom é quase sempre isto:

# RUIM — percorre linha por linha, lento e nada idiomático

    df.loc[i, "total"] = df.loc[i, "preco"] * df.loc[i, "quantidade"]

df["total"] = df["preco"] * df["quantidade"]

    resultados = []
    pagina = 1
    while True:
        response = requests.get(url_base, params={"pagina": pagina}, headers=headers, timeout=10)
        response.raise_for_status()
        dados = response.json()
        if not dados["itens"]:
            break
        resultados.extend(dados["itens"])
        pagina += 1
    return resultados

Retry básico

import time

def get_com_retry(url, tentativas=3, **kwargs):
    for tentativa in range(1, tentativas + 1):
        try:
            response = requests.get(url, timeout=10, **kwargs)
            response.raise_for_status()
            return response
        except requests.exceptions.RequestException as e:
            if tentativa == tentativas:
                raise
            time.sleep(2 ** tentativa)     # backoff exponencial: 2s, 4s, 8s...

Como ler uma documentação de API sem depender de IA

  1. Ache a seção "Authentication" — descobre como enviar credenciais (header, query param, OAuth).
  2. Ache "Base URL" — o prefixo comum de todos os endpoints.
  3. Para cada endpoint que você precisa, veja: método HTTP (GET/POST/...), parâmetros obrigatórios vs opcionais, formato de resposta (geralmente tem um exemplo de JSON).
  4. Veja a seção de rate limits — quantas requisições por minuto são permitidas.
  5. Teste primeiro num cliente HTTP simples (curl, Postman, Insomnia, ou até o próprio requests num script isolado) antes de integrar na automação.

M-18Logging

Não use print() para diagnosticar automação em produção — use logging. print não tem nível, não tem timestamp automático e não vai pra arquivo sem esforço extra.

Configuração básica

    level=logging.INFO,
    format="%(asctime)s - %(levelname)s - %(message)s",
    handlers=[
        logging.FileHandler("automacao.log", encoding="utf-8"),
        logging.StreamHandler()      # também mostra no console
    ]
)

logger = logging.getLogger(__name__)

Níveis (do menos ao mais grave)

logger.debug("valor intermediário: %s", valor)     # detalhe técnico, só em desenvolvimento
logger.info("Processando arquivo vendas.csv")        # progresso normal
logger.warning("Linha 45 ignorada: preço negativo")   # algo estranho, mas não quebrou
logger.error("Falha ao conectar na API")                # algo falhou
logger.critical("Banco de dados inacessível, abortando")  # falha grave, programa não continua

Por que usar %s em vez de f-string no logger: o logger só formata a string se o nível estiver ativo — mais eficiente quando debug() está desligado em produção. Na prática, f-string também funciona e é mais comum hoje — use o que for mais legível para o time.

Diagnosticando uma automação que falhou (uso real)

try:
    processar_arquivo(caminho)
except Exception as e:
    logger.exception(f"Erro ao processar {caminho}")   # loga o erro E o stack trace completo
    # logger.exception só deve ser chamado dentro de um except

logger.exception() grava automaticamente o traceback completo — essencial para descobrir depois onde exatamente o script quebrou, sem precisar reproduzir o erro.

M-21Boas práticas

PEP 8 essencial (o que realmente importa no dia a dia)

  • nomes de variáveis e funções: snake_case (calcular_total, não calcularTotal)
  • nomes de classes: PascalCase (ProcessadorDados)
  • constantes: MAIUSCULO_COM_UNDERSCORE (LIMITE_MAXIMO = 100)
  • indentação: 4 espaços, nunca tab
  • linhas: idealmente até ~88-100 caracteres

Nomes que comunicam intenção

# ruim
def proc(d):
    r = []
    for x in d:
        if x[2] > 0:
            r.append(x)
    return r

# bom
def filtrar_vendas_positivas(vendas):
    return [venda for venda in vendas if venda["valor"] > 0]

Responsabilidade única

Cada função faz uma coisa. Se o nome da função tem "e" no meio ("ler_e_validar_e_salvar"), é sinal de quebrar em 3 funções.

DRY sem exagero

Repetir 2 linhas iguais em 2 lugares não é necessariamente errado. DRY (Don't Repeat Yourself) vale quando a duplicação representa a mesma regra de negócio — se você mudar a regra, teria que lembrar de mudar em vários lugares. Duplicação acidental de estrutura (dois loops parecidos, mas com propósitos diferentes) não precisa virar abstração forçada.

Docstrings e comentários

def calcular_total_com_desconto(preco: float, percentual_desconto: float) -> float:
    """Aplica desconto percentual sobre o preço.

    percentual_desconto deve estar entre 0 e 100.
    """
    return preco - (preco * percentual_desconto / 100)

Comente o porquê, não o o quê (o código já diz o que faz, se estiver bem escrito):

# ruim — só repete o código
# soma 1 no contador
contador += 1

# bom — explica uma decisão não óbvia
# arredonda para cima porque a API cobra por requisição parcial
paginas = math.ceil(total_itens / itens_por_pagina)

Type hints

def calcular_total(valores: list[float]) -> float:
    return sum(valores)

def buscar_cliente(cliente_id: int) -> dict | None:
    ...

Não são obrigatórios, mas ajudam muito quando você volta ao código dias depois — e ferramentas como editores/linters usam isso para te avisar de erros antes de rodar.

Segurança básica

  • nunca deixe senha/token/chave de API direto no código — use variáveis de ambiente (os.environ.get("API_TOKEN")) ou arquivo .env (com python-dotenv), e adicione esse arquivo ao .gitignore.
  • sempre use parâmetros (?) em SQL, nunca concatenação de string.
  • valide dados de entrada externos (arquivo, API, formulário) antes de usar.

Performance — quando se preocupar

Não otimize prematuramente. Escreva código claro primeiro. Só otimize quando: o script está visivelmente lento, e você já identificou (não chutou) onde está o gargalo — normalmente é um loop que deveria ser vetorizado (Pandas) ou uma leitura de arquivo repetida desnecessariamente.

M-22Depuração

O processo (siga nessa ordem, não pule etapas)

  1. Reproduzir o erro — rode de novo, confirme que acontece sempre (ou identifique em que condição acontece).
  2. Ler a mensagem completa — o Python já te diz o tipo do erro e geralmente onde. Não ignore o texto do erro.
  3. Identificar a linha — o traceback mostra a pilha de chamadas; a última linha do seu código no traceback é onde o erro efetivamente ocorreu.
  4. Inspecionar os valores — o que estava dentro da variável naquele momento? Muitas vezes o erro é "o dado não era o que eu esperava", não um erro de lógica.
  5. Isolar o problema — reduza ao menor trecho de código que ainda reproduz o erro (comente partes, teste isoladamente no console).
  6. Criar hipótese — "acho que a coluna X está vindo como string em vez de número".
  7. Testar a hipótese — print(type(valor)), ou inspecione no debugger.
  8. Corrigir.
  9. Testar de novo — inclusive casos que já funcionavam, para não quebrar algo que estava certo.

Lendo um traceback

Traceback (most recent call last):
  File "main.py", line 12, in <module>
    resultado = processar(dados)
  File "src/dados.py", line 8, in processar
    total = valores["preco"] * quantidade
KeyError: 'preco'

Leia de baixo para cima: a última linha (KeyError: 'preco') é o tipo do erro. A linha logo acima mostra o arquivo e a linha exata de código onde ele aconteceu (src/dados.py, linha 8). As linhas de cima mostram a cadeia de chamadas que levou até lá.

print() estratégico

print(f"DEBUG - tipo: {type(valor)}, valor: {valor!r}")   # !r mostra repr, útil pra ver aspas/espaços escondidos

Print estratégico funciona bem para scripts pequenos. Para algo mais complexo, use o debugger.

Debugger (breakpoint nativo)

def processar_linha(linha):
    breakpoint()      # pausa a execução aqui, abre um prompt interativo (pdb)
    total = linha["preco"] * linha["quantidade"]
    return total

No prompt do breakpoint(): n (próxima linha), s (entra na função chamada), c (continua até o fim/próximo breakpoint), p variavel (imprime o valor), q (sai).

No VS Code/PyCharm, prefira o debugger visual (clique na margem para criar um breakpoint) — é mais rápido que breakpoint() manual para depuração recorrente.

Inspeção de variáveis em Pandas

print(df.dtypes)          # tipo de cada coluna — fonte comum de bug
print(df.isna().sum())      # onde tem nulo escondido
print(df.shape)               # linhas/colunas mudaram do esperado?

M-23Como não depender de IA

O objetivo aqui não é "nunca use IA" — é usar IA como última etapa, não como primeira, para não deixar sua fluência atrofiar de novo.

Ordem recomendada quando travar

  1. Tente sozinho primeiro — mesmo que erre, o esforço de tentar é o que reconstrói a memória muscular de sintaxe.
  2. Consulte este manual (ou a documentação oficial) — a maior parte do que trava você já está mapeado aqui.
  3. Pesquise exemplos — Stack Overflow, documentação oficial da biblioteca, changelog.
  4. Depure sistematicamente (Módulo 22) — muitas vezes o erro se resolve sem precisar de mais informação nenhuma, só de olhar com calma.
  5. Só então pergunte à IA — e quando perguntar, peça explicação antes de código pronto.

Como perguntar bem para uma IA (ou para qualquer colega)

Ruim — terceiriza o problema inteiro:

"Faça uma automação que leia essa planilha."

Bom — mostra que você já pensou, já tentou, e pede exatamente o que falta:

"Estou tentando filtrar um DataFrame pela coluna 'status', mas meu filtro retorna vazio. Aqui está meu código e o resultado. Explique o possível problema sem reescrever o código."

Regra de ouro

Nunca copie um trecho de código que você não consegue explicar linha por linha. Se a IA te dá uma solução e você não entende uma parte, pergunte "o que essa linha faz e por quê" antes de usar. Isso é o que separa "recuperar fluência" de "delegar de novo".

Checklist antes de perguntar para IA

  • [ ] Tentei escrever a solução eu mesmo, mesmo que incompleta?
  • [ ] Sei descrever exatamente o que está errado (não só "não funciona")?
  • [ ] Tenho o erro/traceback completo, não só um resumo?
  • [ ] Sei o que eu esperava que acontecesse vs o que aconteceu?
  • [ ] Estou pedindo explicação, e não só código pronto?

M-24Orquestração com Prefect

Prefect serve para transformar scripts soltos em fluxos observáveis, agendáveis e com retry automático. Testado com Prefect 2.x (a versão 3.x manteve os conceitos de @task/@flow, mas alguns detalhes de deploy mudaram — confira a documentação oficial se for colocar em produção).

Por que usar Prefect em vez de só rodar o script

Sem Prefect Com Prefect
erro derruba o script inteiro retry automático por task
sem visibilidade do que rodou UI com histórico de execuções
agendamento via cron manual schedules integrados
logs espalhados logging centralizado por execução
difícil saber onde travou cada task tem status próprio (rodando, falhou, retry)

@task e @flow — o básico

from prefect import flow, task

@task
def extrair_dados(caminho):
    return pd.read_csv(caminho)

@task
def validar_dados(df):
    return df.dropna(subset=["valor"])

@task
def salvar_resultado(df, caminho_saida):
    df.to_csv(caminho_saida, index=False)

@flow
def pipeline_vendas(caminho_entrada: str, caminho_saida: str):
    df = extrair_dados(caminho_entrada)
    df_validado = validar_dados(df)
    salvar_resultado(df_validado, caminho_saida)

if __name__ == "__main__":
    pipeline_vendas("vendas.csv", "vendas_tratadas.csv")

Isso já é praticamente idêntico ao padrão ENTRADA → VALIDAÇÃO → PROCESSAMENTO → SAÍDA do Módulo 2 — Prefect só adiciona observabilidade em cima de funções que você já escreveria de qualquer forma.

Retry automático

@task(retries=3, retry_delay_seconds=10)
def consultar_api(url):
    response = requests.get(url, timeout=10)
    response.raise_for_status()
    return response.json()

Se a task falhar (exceção não tratada), o Prefect tenta de novo automaticamente até 3 vezes, esperando 10 segundos entre tentativas — sem você escrever try/except com loop manual.

Logging dentro do flow

from prefect import get_run_logger

@task
def processar_arquivo(caminho):
    logger = get_run_logger()
    logger.info(f"Processando {caminho}")
    ...

Esse log aparece tanto no console quanto na UI do Prefect, associado à execução específica — mais útil que print() porque fica rastreável por execução.

Rodando tasks em paralelo com .submit()

@flow
def processar_varios_arquivos(arquivos: list[str]):
    futures = [processar_arquivo.submit(arq) for arq in arquivos]
    resultados = [f.result() for f in futures]
    return resultados

.submit() dispara a task de forma assíncrona (não bloqueia até terminar); .result() espera e pega o valor. Útil quando você tem várias tasks independentes (ex.: processar vários arquivos, consultar várias APIs) e quer rodar em paralelo em vez de sequencialmente.

Subflows (compor pipelines menores)

@flow
def etl_vendas(caminho):

@flow
def pipeline_completo():

Parâmetros e agendamento

@flow
def pipeline_diario(data_referencia: str = None):
    data = data_referencia or date.today().isoformat()
    ...

Para rodar com agendamento recorrente (ex.: todo dia às 6h), o caminho atual do Prefect é flow.serve() (Prefect 2.19+) ou criar um deployment via CLI (prefect deploy), associando um schedule (cron). Como essa parte muda com frequência entre versões, ao configurar produção confirme a sintaxe exata na documentação oficial do Prefect para a versão instalada no seu ambiente:

if __name__ == "__main__":
    pipeline_diario.serve(name="pipeline-vendas-diario", cron="0 6 * * *")

Rodando a UI localmente

Lá você acompanha execuções, vê logs, reexecuta flows que falharam, e visualiza o histórico — substitui boa parte do trabalho manual de checar arquivo de log.

M-27Pipelines de dados e dashboards

Desenhando um pipeline de dados (retomando o Módulo 2, agora com estrutura de produção)

FONTES (CSV, API, banco) 
    ↓
EXTRAÇÃO (ler cada fonte)
    ↓
VALIDAÇÃO (schema, tipos, nulos)
    ↓
TRANSFORMAÇÃO (limpar, calcular, padronizar)
    ↓
CARGA (salvar em banco/arquivo consolidado)
    ↓
DASHBOARD (ler o resultado consolidado, nunca as fontes brutas)

Regra prática: o dashboard nunca deve processar dado bruto na hora de exibir — ele lê o resultado já tratado pelo pipeline. Isso separa "processamento pesado" (roda uma vez, agendado) de "visualização" (precisa ser rápida sempre que alguém abre a tela).

Estruturando o pipeline com as ferramentas já vistas

# pipeline.py
from prefect import flow, task
import pandas as pd
import sqlite3

@task(retries=2)
def extrair_vendas():
    return pd.read_csv("vendas.csv")

@task
def transformar(df):
    df = df.dropna(subset=["valor"])
    df["valor"] = df["valor"].astype(float)
    return df.groupby("categoria")["valor"].sum().reset_index()

@task
def carregar(df):
    with sqlite3.connect("dashboard.db") as conexao:
        df.to_sql("resumo_vendas", conexao, if_exists="replace", index=False)

@flow
def pipeline_dashboard():
    df = extrair_vendas()
    resumo = transformar(df)
    carregar(resumo)

if __name__ == "__main__":
    pipeline_dashboard()

Isso pode ser agendado com flow.serve(cron=...) (Módulo 24) para rodar todo dia antes de alguém abrir o dashboard.

Cache — por que importa

    ...

Sem cache, o Streamlit reexecuta o script inteiro a cada interação do usuário (cada clique, cada filtro mudado). Para qualquer consulta a banco/API/arquivo grande, o cache é o que evita o dashboard ficar lento — essa é a causa mais comum de "meu dashboard trava" em quem está começando com Streamlit.

Quando Streamlit não é suficiente

Para dashboards com múltiplas páginas complexas, controle fino de layout/callbacks, ou uso corporativo com muitos usuários simultâneos, considere Dash (também Python, baseado em Plotly, mais verboso mas mais flexível) ou uma ferramenta de BI dedicada (Power BI, Metabase) alimentada pelo banco que seu pipeline já popula — nesse caso o pipeline Python continua sendo o mesmo, só muda a camada de visualização.

Desafios progressivos

Não escolares. Progressivos em complexidade real de automação. Sem solução — o objetivo é você chegar até ela usando este manual.

Nível 1 — Organizador de arquivos

Problema: você tem uma pasta com arquivos bagunçados de vários tipos. Requisitos: organizar automaticamente por extensão, em subpastas. Restrições: não pode sobrescrever arquivo existente com mesmo nome (renomear ou pular). Dados fictícios: pasta com .pdf, .jpg, .csv, .docx, alguns sem extensão. Resultado esperado: subpastas pdf/, jpg/, csv/, etc., cada uma com os arquivos correspondentes. Possíveis extensões: logar quantos arquivos foram movidos por tipo; ignorar arquivos ocultos.

Nível 2 — Processador de CSV

Problema: um CSV de vendas tem linhas com dados inválidos (preço negativo, campos vazios, texto em vez de número). Requisitos: ler o CSV, validar linha por linha, separar válidas de inválidas, salvar dois arquivos de saída. Restrições: não pode quebrar o script se uma linha estiver malformada. Dados fictícios: CSV com colunas produto, preco, quantidade, algumas linhas com preco vazio ou negativo. Resultado esperado: vendas_validas.csv e vendas_invalidas.csv, com motivo da invalidação na segunda. Possíveis extensões: gerar um resumo (quantas válidas, quantas inválidas, motivo mais comum).

Nível 3 — Consolidador de várias planilhas

Problema: uma pasta tem uma planilha Excel por mês (jan.xlsx, fev.xlsx, ...), todas com as mesmas colunas. Requisitos: juntar tudo em uma única tabela, identificando de qual mês cada linha veio. Restrições: planilhas podem ter colunas em ordem diferente; trate isso. Dados fictícios: 3-4 arquivos .xlsx com colunas data, produto, valor. Resultado esperado: um consolidado.xlsx com todos os dados e uma coluna extra mes_origem. Possíveis extensões: detectar e alertar se algum arquivo tem coluna faltando.

Nível 4 — Gerador automático de relatório

Problema: a partir de uma base de dados de vendas, gerar um relatório executivo. Requisitos: total geral, total por categoria, top 5 produtos, tudo em um Excel formatado (cabeçalho em negrito, cores). Restrições: o relatório deve ser gerado com um único comando (python gerar_relatorio.py). Dados fictícios: base com produto, categoria, valor, quantidade, data. Resultado esperado: arquivo .xlsx com múltiplas abas: "Resumo", "Top Produtos", "Por Categoria". Possíveis extensões: adicionar gráfico; enviar o relatório por e-mail automaticamente.

Nível 5 — Consumidor de API

Problema: consumir uma API pública paginada e salvar os dados localmente. Requisitos: paginação completa, tratamento de erro de rede, respeitar rate limit. Restrições: não pode perder dados se a API falhar no meio — salvar progresso incrementalmente. Dados fictícios: use uma API pública de teste (ex.: uma API REST de exemplo com paginação). Resultado esperado: um CSV/JSON com todos os registros coletados. Possíveis extensões: retry automático com backoff; log de quantas páginas foram coletadas.

Nível 6 — ETL completo

Problema: dados brutos de múltiplas fontes (CSV + Excel) precisam virar uma base limpa e analisável. Requisitos: Extract (ler várias fontes), Transform (limpar, padronizar tipos, remover duplicatas), Load (salvar em SQLite). Restrições: o processo deve poder rodar de novo sem duplicar dados (idempotência básica). Dados fictícios: um CSV de clientes e um Excel de pedidos, com alguma inconsistência de formato entre eles. Resultado esperado: banco dados.db com tabelas limpas, prontas para consulta SQL. Possíveis extensões: logging detalhado de cada etapa; validação de integridade (pedido referencia cliente existente?).

Nível 7 — Automação combinada (arquivos + API + Pandas + Excel)

Problema: todo dia, o sistema deve: ler arquivos novos de uma pasta, enriquecer os dados consultando uma API externa, consolidar tudo com Pandas, e gerar um relatório Excel formatado, com log completo da execução. Requisitos: todas as etapas anteriores combinadas em um único fluxo orquestrado. Restrições: deve ser resiliente — se a API falhar para um item, o processo continua para os demais e reporta no final quais falharam. Dados fictícios: arquivos CSV de pedidos + uma API fictícia de consulta de CEP/status de cliente. Resultado esperado: relatório final .xlsx + arquivo de log com o resumo da execução (quantos processados, quantos falharam, tempo total). Possíveis extensões: transformar em projeto estruturado (Módulo 19), com testes (Módulo 20) para as funções de transformação.
